案件で**継続的に守る制約・規約**を `Cortex/Rules/records/` 配下に **1ルール1ファイル** で登録・更新します。スキーマ・運用ルールは `Cortex/Rules/README.md` を参照。

## 目的

「本番リリースは金曜禁止」「決済処理は必ず二重確認を通す」のような、**その後もずっと効き続ける約束事**を Gold 層のエンティティにする。AI エージェントがこの制約を知らずに動くと事故になる（禁止された曜日にデプロイ手順を案内する等）ため、機械可読なレコードにして巡回エージェント・AIS が frontmatter から「守るべき線」を把握できるようにする。

## Decision との違い（起票前に判別する）

- **Decision** = 経緯のある一回の決定（過去の出来事・凍結型）。「Next.js を採用した」
- **Rule** = 継続的に守る制約（今も効いている約束事）。「本番リリースは金曜禁止」

一回の決定は Rule にしない（`update-decision` で扱う）。Decision から蒸留された Rule（「金曜リリース禁止を決定した」という Decision から「金曜リリース禁止」という Rule を立てる）は `relations` の `derived_from` で元 Decision（`YYYYMMDD-NNN`）を指す。

> 夜間の `update-gold`（Phase D）が、その日の差分ソースから継続的な制約だけを**用語より一段保守的に**抽出し `status: draft` で起票する。本スキルは**人間の手動起票・更新の口**であり、draft の確認・`active` 昇格や、明示的に合意された制約の登録を扱う。

## 実行手順

### 1. 既存のルールと除外リストを読み込む

`Cortex/Rules/records/*.md` の frontmatter を読み、既存の `title` の集合を把握する（重複登録の照合に使う）。あわせて `Cortex/Rules/README.md` の「除外ルール」セクションに列挙された制約を把握する：

```bash
grep -hE '^title:' Cortex/Rules/records/*.md 2>/dev/null || true
```

### 2. 情報源から制約候補を抽出する

`$ARGUMENTS` で情報源（ファイルパス・Decision の ID・ルールそのもの）が指定された場合はそれを優先する。指定がない場合は以下を走査する：

- `Cortex/Decisions/records/` の決定のうち、**継続的な制約として効き続けるもの**（そこから Rule を蒸留する）
- `会議/` の議事録・`課題管理/issues/` の課題で、「今後も守る」「常に〜する」「〜は禁止」「原則〜する」等の**継続的に効く約束事として明示的に合意されたもの**

**抽出対象**: その後もずっと効き続ける制約・運用ルールとして明示的に合意されたものだけ。
**除外**: 一回きりの意思決定（＝Decision）・単発の TODO/アクションアイテム・期限付きの依頼・推測。ソース中に制約として明示的に合意された根拠が無いものは起票しない。**用語より一段保守的に判断し、確信が持てなければ起票しない**（Rule は AI の行動を直接制約するため誤起票のコストが高い）。

### 3. 既存ルール・除外リストとの照合

抽出した候補をステップ1の集合と照合する：

- **既存ルールと重複または実質同一** → 新規ファイルを作らない（必要なら既存ファイルの本文更新を提案する。変更履歴は git が持つ）
- **除外リストに該当** → スキップする（過去にレビューで却下された制約の再追加防止。除外リスト自体は編集しない＝読むだけ）
- **新規の制約** → `Cortex/Rules/template.md` ベースの新規ファイルを提案する

### 4. プレビューと承認（必須）

登録・更新する内容（新規／本文更新の別、ファイル名、`title`、`description`、`status`、`relations`）を提示し、ユーザーの承認を得てから書き込む。**承認なしに書き込まない。**

- 起票するルールは原則 **`status: draft`**（AI 生成・人間未確認の印）にする
- **対話でユーザー本人が制約の内容に合意している場合に限り `status: active` にしてよい**（本人合意の無いものを勝手に active にしない）

### 5. ファイルの作成・更新

- ファイル名: `records/{slug}.md`、ID: `rule:{slug}`（例: `rule:本番リリース-金曜禁止`）
- `title` に制約の1行表現、`description` に制約の1文要約（一覧・検索・外部消費で使う）を必ず記入する
- **出典**: Decision から蒸留する場合は `relations` の `derived_from` で元 Decision（`YYYYMMDD-NNN`）を、議事録・課題から直接読み取れる制約なら `based_on` で安定ID（`minute:{定例名}:{YYYYMMDD}`・課題キー等）を指す。安定IDが分からなければ relations は付けない（ファイルパスは書かない）
- 効かなくなったルールは削除せず、置き換える Decision から履歴をたどれるようにする
- **コミット前に `node "<SKILL_DIR>/../../scripts/validate-cortex.mjs"`（プラグイン同梱リンター）を実行し、規約違反があれば修正してからコミットする**

## 注意事項

- **同一の制約に複数ファイルを作らない**（重複は既存ファイルに集約する）
- **用語より保守的に**: 継続的に守る制約として明示的に合意された根拠があるものだけを起票する（一回の決定・単発TODO・推測は起票しない）
- 「除外ルール」リストは読むだけで編集しない（編集は人間のレビュー時のみ）
- 出典となる Bronze のドキュメント（`課題管理/` 等）は読むだけで編集しない
- frontmatter のフィールドは `Cortex/Rules/README.md` で定義されたもの以外を追加しない
