# migrations — データスキーマのマイグレーション

エンジンの更新が**案件リポのデータ側**（frontmatter・ディレクトリ構造・CLAUDE.md のエンジン管理ブロック）の変更を要する場合、ここにマイグレーションを追加する。エンジン（コード）は中央で上がるが、各案件リポに散在するデータは自動では変わらない——その結合点を機構で解くのがこのディレクトリの役割。

## ファイル規約

- ファイル名: `NNNN-説明.mjs`（NNNN は 4 桁連番）
- 必須エクスポート:

```js
export const meta = {
  to: 2,                          // 適用後の schema_version
  description: "何をする変更か",
};

export async function run(repoRoot) {
  // 冪等に書くこと（2回実行しても壊れない）
};
```

## 動作

- 案件リポの `Cortex/Home.md` frontmatter `engine.schema_version` が現在値（未宣言は 0）
- `engine-migrate.yml`（案件リポのスタブから夜間 cron）が `scripts/engine-migrate.mjs` を実行し、**未適用分をすべて**番号順に適用して schema_version を書き進める
- 途中で例外が出たら実行を失敗（赤）で終える。**その回のコミットは行わない**（中途半端に適用された状態を push させない）。マイグレーションは冪等なので、直したうえで再実行すれば続きから適用される
- 夜間の精製系ワークフローは、案件の schema_version がエンジン最新より古い場合スキップする（半端なスキーマで走らせない）。判定は `scripts/schema-current.mjs`

## 人手適用のゲートは持たない（`autoApply` は廃止した）

かつて `autoApply: false` という「人間レビュー必須」のフラグがあったが、**外した**。

理由は実態がそうなっていなかったこと。34 件中 2 件にしか付いておらず、しかもどちらも理由は「`.github/workflows/` を触るので `GITHUB_TOKEN` では push できない」という技術的制約だった。レビューする人は現れないまま、**人手待ちの後ろに積まれたマイグレーションを「適用しては捨てる」状態になり、艦隊 9 案件が止まった**（schema_version が進まないので Gold 昇格まで沈黙した）。気づけたのは偶然で、放っておけば**人が手で当てるまで毎晩同じことを繰り返し続ける**設計だった。**動かないゲートは安全装置ではない。**

いまは `FLEET_WORKFLOW_TOKEN`（Contents + Workflows の書き込み権）で push するので、ワークフローファイルを触るマイグレーションも自動で配れる。

### では危険な変更はどう止めるか

- **レビューはエンジンの PR で行う**（マイグレーションはコードなので、そこが唯一のレビュー地点）
- **破壊的な書き換えを書かない**のが第一。Gold 層の運用原則どおり、自動化は新規追加・機械変換にとどめ、既存レコードの意味を変える書き換えはマイグレーションで行わない
- 消す場合は 0018 の型に倣う。**機械生成物だと条件で確かめられるものだけ消し、人の起票が混ざっていたら何もせず警告して残す**
- 1 マイグレーション = 1 スキーマ版。まとめない

## 止まったときの気づき方（通知）

- マイグレーションがエラーで失敗した場合、engine-migrate は **失敗（赤）** になる。GitHub の失敗通知が届き、Actions 画面でも赤く見える
- 停止中は精製系ワークフローも schema_version が古いためスキップされる（半端なスキーマで走らせない）。**ただし run 自体は緑のまま AI ステップだけ skip される**ので、赤いのは engine-migrate だけである点に注意
